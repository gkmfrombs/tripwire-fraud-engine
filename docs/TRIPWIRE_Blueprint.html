TRIPWIRE.
MONITORING

Project Blueprint

A local Kubernetes MLOps pipeline that watches transaction streams and flags fraud in real time — built end-to-end without a single managed cloud service.

01 / PROBLEM STATEMENT

Why this exists

In finance and e-commerce, a fraud check has milliseconds to make a call. The hard part was never the model — it's the infrastructure that gets fresh features to that model, keeps it accountable, and catches the moment it starts drifting from reality.

Managed cloud platforms hide most of that machinery behind a dashboard. TRIPWIRE strips the cloud away and rebuilds the whole chain — storage, feature serving, training, deployment, monitoring — as a self-contained system running on one machine. Nothing here is simulated infrastructure; every piece is the real open-source tool a production team would reach for.

02 / TECHNICAL APPROACH

The stack

  • MinIO + DVCLocal S3-compatible object storage, with every dataset version tracked
  • Feast + RedisFeature store serving rolling user features at sub-millisecond latency
  • MLflowExperiment tracking and the model registry of record
  • PrefectOrchestrates ingestion, validation, and retraining as one flow
  • GitHub ActionsTests and builds the service on every push
  • FastAPI + MinikubeServes predictions from a real local Kubernetes cluster
  • Evidently AIWatches live traffic for statistical drift against training data
03 / SYSTEM FLOW

How data moves through it

Every arrow below is a real network hop between two running services — nothing here is a diagram of intent, it's a diagram of what actually gets deployed.

Raw Transactions→ MinIO + DVC→ Validation→ Feast + Redis→ XGBoost Training→ MLflow Registry→ Docker Build→ Minikube + FastAPI→ Live Prediction→ Evidently AI

If Evidently AI detects drift in the live traffic, the loop feeds back into training — the model retrains on fresher data instead of quietly going stale.

04 / HARDWARE REALITY CHECK

Can your machine actually run this

Running all seven tools plus Minikube at once is genuinely heavy. Know this going in rather than discovering it mid-build.

SetupRAM neededNotes
Full stack — every tool + Minikube16–32 GBExpect slowdowns under 16GB
Lite path — skip Feast/Redis, run FastAPI directly in Docker instead of Minikube8 GBSame concepts, lighter footprint

If your machine chokes at Feast or Minikube, switch to the lite path rather than fighting it. A working simple system beats a crashed complex one — and explaining that trade-off is itself a legitimate engineering story.

05 / REPOSITORY SETUP

Before the first line of model code

A clean repository signals discipline before anyone opens a single file. Set the structure now, not after the pipeline exists.

setup — initialize repository
mkdir tripwire-fraud-engine
cd tripwire-fraud-engine
git init
echo "# TRIPWIRE — Real-Time Fraud Risk Engine" > README.md
git add README.md
git commit -m "Initial commit"
setup — scaffold directories
mkdir -p data/raw data/processed
mkdir -p notebooks
mkdir -p src/data src/features src/models src/api
mkdir -p kubernetes/deployments kubernetes/services
mkdir -p .github/workflows
touch .gitignore requirements.txt Dockerfile

Add Python, Jupyter, and OS artifacts to .gitignore — and add data/ too. Large datasets belong in MinIO and DVC, never in Git history.

06 / EXECUTION PHASES

The build sequence

01

Infrastructure Foundations

Goal — stand up the storage and tracking backbone.

  • Write a docker-compose.yml to run MinIO and MLflow together
  • Point MLflow's artifact store at MinIO
  • Confirm both dashboards load on localhost
02

Data Versioning & Feature Engineering

Goal — get real-world-grounded data flowing and features ready to serve.

  • Load the PaySim dataset — synthetic mobile-money transactions built from real transaction logs, with human-readable fields
  • Push the raw data to MinIO, initialize DVC with MinIO as the remote
  • Cross-check the dataset's fraud-category split against RBI's real fraud statistics (data.gov.in) — flag and document any mismatch instead of hiding it
  • Define entities and feature views in Feast, materialize to Redis

No government agency publishes raw transaction-level fraud data — that's a privacy-law limit, not a research gap. PaySim is the accepted substitute used across fraud-detection research; RBI's real aggregate stats are used here only to check plausibility, not to train on.

03

Model Training & Orchestration

Goal — train, track, and automate.

  • Train an XGBoost model in src/models
  • Autolog hyperparameters, F1, and recall to MLflow
  • Chain ingestion → features → training into one Prefect flow
04

Containerization & Minikube Deployment

Goal — move the model off your laptop and onto a cluster.

  • Wrap the model in a FastAPI service that loads from MLflow
  • Build the Docker image, start Minikube
  • Apply Deployment, Service, and HPA manifests
05

CI/CD & Continuous Monitoring

Goal — keep the system honest after launch.

  • Run pytest on every push via GitHub Actions
  • Simulate live traffic against the cluster's API
  • Generate Evidently AI drift reports from prediction logs
07 / SUCCESS CRITERIA

How you'll know it's actually done

  • A transaction sent to the API returns a fraud probability in under ~200ms
  • MLflow shows at least 3 experiment runs with different hyperparameters
  • One model is marked "Production" in the MLflow Model Registry
  • You can trace exactly which data version trained the current model
  • A push to GitHub triggers an automatic redeploy
  • An Evidently AI report shows a real drift comparison between two data windows
